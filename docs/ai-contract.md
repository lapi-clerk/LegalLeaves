# AI出力 JSON契約

楽々mintsが読み込む「AIの整理データ」の形式仕様。プロンプト（[`../prompts/`](../prompts/)）はこの契約を満たすJSONを出力すること。

- **実v1スキーマ（[`../prompts/v1.md`](../prompts/v1.md)）を土台に、描画指示 `stamp{}` を追加しただけ**の後方互換版。
- v1の項目名（`evidence_number`, `branch_range`, `evidence_explanation`, `confidence`, `notes`）はそのまま維持。
- `stamp` を持たないファイルは従来どおり（回転・押印なし）動作する。
- 未知の項目はアプリ側が無視してよい。AIが項目を省略した場合は「既定値」を適用する。

---

## トップレベル

```jsonc
{
  "schema_version": "2.0",          // 文字列。省略時は "1.0" 相当とみなす
  "evidence_explanation": { ... },  // v1から継続（証拠説明書ファイル自体の情報）
  "case": { ... },                  // 任意・v3先取り（事件メタ）。evidence_explanationとは別物
  "files": [ FileEntry, ... ],      // 必須
  "warnings": [ "string", ... ]     // 任意
}
```

### `evidence_explanation`（v1から継続）
**証拠説明書というファイルそのもの**についての情報。証拠番号スタンプとは無関係。
```jsonc
"evidence_explanation": {
  "exists": true,                                  // 証拠説明書があるか
  "file_name": "証拠説明書.pdf",                    // その元ファイル名。なければ null
  "first_evidence_number": "甲001",                // 説明書がカバーする最初の番号
  "last_evidence_number": "甲003",                 // 同・最後の番号
  "suggested_file_name": "証拠説明書(甲001～甲003).pdf"
}
```

> **パターンA（証拠説明書の参照・v3フェーズ1）**: `evidence_explanation.exists=true` のとき、証拠説明書が
> **番号の正**。AIは各証拠の `evidence_number`/`title` を説明書に合わせ、独断で振り直さない。食い違い（説明書にあるが
> ファイルが無い／その逆／番号・標目のズレ）は当該ファイルの `needs_user_confirmation=true`。
> アプリは `first/last_evidence_number` の範囲と実ファイルの号証番号を突き合わせ、**不足・範囲外**を照合画面に表示する
> （整合チェック）。説明書ファイル自体は `type:"証拠説明書"`＝スタンプせずリネームのみ。

### `case`（任意・v3先取り）
証拠説明書の自動生成（v3）に使う**事件メタ情報**。`evidence_explanation` とは役割が違う（あちらはファイル情報）。v2アプリは保存のみで使わない。
```jsonc
"case": {
  "case_name": "貸金返還請求事件",
  "case_number": "令和6年(ワ)第123号",
  "court": "東京地方裁判所",
  "plaintiff": "株式会社アルファ商事",   // 原告名（v3-B ヘッダ用）
  "defendant": "ベータ工業株式会社",     // 被告名
  "party": "原告",                       // この提出者の側（原告/被告）
  "lawyers": ["弁護士 山田太郎"]         // 提出者側の代理人
}
```
> **取得元の限定（v3-B・重要）**: `case` は**本件の主張書面（訴状・準備書面など当事者自身の書面）からのみ**埋める。
> 証拠（裁判例・書籍・資料）の中身にある事件番号・当事者・弁護士名を本件情報として使わない。読み取れなければ null。
> アプリはこれで証拠説明書のヘッダ（裁判所・事件番号・当事者・代理人）を埋め、空なら ●● のまま（弁護士が記入）。

## FileEntry

> **全角・半角の使い分け**: `original_file_name` は元ファイル名を一字一句そのまま（幅を変えない）。
> それ以外の内容欄（`title`/`suggested_base_name`/`author`の人名部分/`proof_purpose`等）は
> 英数字・スペース・括弧を**全角**で（氏名は姓名の間に全角スペース）。
> **ファイル名としての幅調整（半角化）はアプリ側（`toHalfWidthFilenamePart`）が行う**ので、
> AIは内容欄を素直に全角で書けばよい。証拠説明書テーブルの整形も同様にアプリ側（`toFullWidth`）が担う。

### v1から継続（既存）
```jsonc
{
  "original_file_name": "scan001.pdf",   // 突き合わせキー。実ファイル名と一致させる
  "type": "証拠",                         // 主張系|証拠説明書|証拠|関連事件の申立|その他
  "evidence_number": "甲001",            // 記号＋ゼロ埋め3桁。証拠以外や不明は null
  "branch_range": null,                  // 枝番。"2" や "1～3"。なければ null
  "title": "契約書",                      // 文書の表題／証拠説明書の標目
  "suggested_base_name": "甲001_契約書",  // 提出用ファイル名（拡張子なし）
  "confidence": "high",                  // high|medium|low
  "needs_user_confirmation": false,
  "confirmation_question": null,
  "notes": "",
  "title_from_file": null,               // v3-A: 標目が説明書と食い違うとき、ファイル中身側の標目。無ければ null
  "author": null,                        // v3-B: 作成者（役割名なら「被告代理人」等）
  "author_alt": null,                    // v3-B: 役割名にしたときの実名（弁護士名/当事者名）。アプリで役割名/実名を選択
  "created_date": null,                  // v3-B: 作成年月日。半角和暦略記「R6.4.12」(令和R/平成H/昭和S)
  "proof_purpose": null,                 // v3-B: 立証趣旨の下書き（確定は弁護士）
  "original_or_copy": null,              // v3-B: 「原本」/「写し」/ null（v3.5: null＝民訴法231条の2の電磁的記録として提出）
  "digitized_from_paper": null,          // v3.5: 紙をスキャン/撮影して電子化した証拠なら true。備考「紙を電子化」の自動記載に使用
  "capture_kind": null,                  // v3-B: 「写真」/「スクリーンショット」/「動画」/ null
  "capture_subject": null,               // 撮影対象
  "capture_datetime": null,              // 撮影日時（半角和暦 R6.4.12）
  "capture_location": null,              // 撮影場所（写真・動画のみ）
  "capture_by": null                     // 撮影者
}
```

> **写真・スクリーンショット・動画（v3.7・FB-14案B）**: `capture_kind` があるものも証拠説明書は**他の証拠と同じ6列の行**で記載する
> （公式ひな形に結合行の様式は無い）。アプリ側の整形: 標目=`title`＋2行目（撮影対象：●●／撮影場所：●●）、
> 作成年月日=`capture_datetime`（撮影日）、作成者=`capture_by`（撮影者）＝民訴規則148条（撮影の対象・日時・場所の明示）を充足。
> `title` は種別が分かる簡潔な語でよい。旧v3-Bの「標目〜作成者を結合したブロック行」は廃止。

> **`author`/`created_date`/`proof_purpose`/`original_or_copy`（v3パターンB・任意）**: 証拠説明書が**無い**とき、アプリが
> 証拠説明書(.docx)を下書き生成するために各「証拠」に入れる。`proof_purpose`（立証趣旨）は**必ず下書き**扱いで確定は弁護士。
> 生成表の体裁（v3.5・公式ひな形 shouko_setsumeisho_f3.xlsx 準拠）: 号証欄は「乙041-1」形式
> （**半角英数・ゼロ埋め3桁・枝番は半角ハイフン**。第/号証なし。**枝番は各行**）、標目・作成者・立証趣旨の英数字は全角、
> 作成年月日は半角和暦。原本/写しは独立列ではなく**標目セル内の2行目に「（原本）」「（写し）」**として入り、
> どちらの記載も無い標目は「民訴法231条の2の電磁的記録として提出」の意味を持つ（定型注記がテンプレに焼き込み済み）。
> これらの整形は**アプリ側が行う**（AIは素の値を入れてよい）。
>
> **`original_or_copy` の判定基準（v3.5・改正民訴法対応）**: 「原本」＝相手方が成立の真正を争い得る重要書類
> （①処分証書＝契約書・合意書・覚書等の署名押印書類 ②筆跡が意味を持つ手書き書面 ③領収書・手形・小切手）。
> null＝電磁的記録として提出（メール/LINEスクショ/Web印刷物/文献・裁判例・公的書類のコピー/写真・音声・動画）。
> 「写し」＝**原則書かない**。紙の証拠で写ししか手元になく、電磁的記録としてではなく**あえて書証として**
> 申し出る例外的な場合のみ（公式記載要領※2）。迷えば `needs_user_confirmation:true`。
> `digitized_from_paper:true` かつ `original_or_copy:null` のとき、アプリが備考欄に「紙を電子化」と自動記載する。

> **`title_from_file`（v3パターンA・任意）**: 証拠説明書の標目（=`title`に入れる正）と、実ファイルの中身から読み取れる標目が
> 食い違うときだけ、ファイル側の標目を入れる。アプリは確認画面で「文書名の採用元＝説明書／ファイル」のワンクリック切替を出す
> （既定は説明書＝`title`）。食い違いが無ければ省略/`null`。

> **番号の使い分け**:
> - `evidence_number` = 照合・並び順の正（**ゼロ埋め3桁**「甲001」。甲001/甲002…甲010 が正しく並ぶ）。
>   記号は複数文字可（企業間訴訟の系列「甲A001」等。スタンプは「甲A第1号証」になる）。
>   原告・申立人＝甲、被告・相手方＝乙が原則で、アプリは食い違い（原告なのに乙等）を照合画面で警告する。
> - ファイル名（`suggested_base_name`）も同じゼロ埋め書式を使う。
> - `branch_range` = ファイル全体の枝番範囲（ファイル名・証拠説明書の表示用サマリ）。
> - 紙面に押すスタンプ表記「**甲第1号証**」は、**アプリが `evidence_number`＋各スタンプの `branch` から自動生成**する（下記）。AIはスタンプ文字列を出力しない。

### v2で追加（任意）— `stamps`（ページごとの配列）
**回転と押印の描画指示**。この項目（または空配列）が無ければ回転も押印もしない（v1と同じ挙動）。
**1ページ＝1要素**。枝番は1ファイル内で複数あり、かつ**1つの枝番が複数ページにまたがる**ことがあるため
（請求書＋領収書の2枚組など）、ページと枝番の対応は機械では決められない。**AIがページごとに `branch` を割り当てる**。
スタンプ文字列はここには持たせない（アプリが生成）。AIは「どのページに」「どの枝番を」「どの向き・位置で」だけ判断する。
```jsonc
"stamps": [
  {
    "page": 1,                 // 対象ページ（1始まり）。1ページにつき1要素
    "branch": "1",             // このページに押す枝番。枝番なしの号証は null
    "draw_label": true,        // true=番号を押す / false=回転のみ（手書き済み等）
    "rotate_degrees": 0,       // 正立させる補正角。0|90|180|270（時計回り）。既定 0
    "position": {              // 「正立表示した紙面」基準の正規化座標
      "x": 0.93,               // 左端=0, 右端=1
      "y": 0.05,               // 上端=0, 下端=1
      "anchor": "top-right"    // (x,y) に合わせるラベル枠の基準点
    },
    "font_size_pt": 18,        // 既定 18（省略可）
    "color": "#C80000"         // 既定 朱色寄りの赤（省略可）
  }
]
```

> **どのページに押すか（運用ルール）**:
> - 原則 AI が内容・ファイル名を見て判断する。**少しでも確証が持てなければ `needs_user_confirmation: true`** にして
>   `confirmation_question` で人間に確認する。
> - 枝番ごとに**別PDFに分かれている**場合は、その先頭ページだけに押せばよい。
> - 1つの枝番が複数ページにまたがる場合（2枚組など）は、原則その枝番の**先頭ページ**に1回。続きのページは
>   `stamps` に入れない（押さない）。判断に迷うときは確認に回す。
> - **1つのPDFに複数の枝番がまとめてスキャンされている場合**は、各枝番の先頭ページに、その枝番を `branch` に
>   入れた要素を作る（`branch_range` は全体の範囲 "1～2"）。区切りの手がかりは ①証拠説明書の枝番ごとの行
>   ②主張書面の引用（「請求書（甲5の1）」等） ③紙面の変化、の順。区切り・枝番ごとの標目・根拠を
>   `confirmation_question` に書き、**必ず** `needs_user_confirmation: true`。根拠が弱ければ区切らずに確認に回す。
>   アプリは `stamps[].branch` が2種類以上あるファイルについて、確認画面の「ページで枝番に分ける」の入力欄へ
>   区切り（例 "1-3, 4-5"）を下書きする。**分けるのは人が確認してから**（自動では分けない）。分けた枝番は
>   出力時に元PDFから該当ページを切り出し、同じ号証番号どうしで1つのPDFに結合する（`sources[].pages`）。

## スタンプ文字列の生成（アプリ側ルール）

各 `stamps[]` 要素ごとに、`evidence_number` と**その要素の `branch`** から、アプリが決定的に生成する。

1. `evidence_number` を `記号` と `番号` に分解（例: `"甲001"` → 記号`甲`, 番号`1`）。
   正規表現の目安: `^(\D+)0*(\d+)$`。
2. 基本形 = `{記号}第{番号}号証`（**ゼロ埋めは外す**。例: `甲第1号証`）。
3. その要素の `branch` があれば末尾に `の{branch}` を付ける（例: `甲第1号証の1` / `甲第1号証の2`）。
4. 押すのは `evidence_number != null` かつ その要素の `draw_label != false` のときだけ。

> 例: `evidence_number:"乙012"`, `branch:null` → **乙第12号証**
> 例: `evidence_number:"甲001"`, `branch:"1"` → **甲第1号証の1**
> （ページごとに `branch` が変わるので、1ファイルから 甲第1号証の1・の2… が生成される）

## 同一号証の自動結合（v2）

枝番が**別ファイルに分かれている**場合、提出時は1つの号証PDFに結合する。これは
**アプリが `evidence_number` をキーに自動で行う**（AIは結合自体を指示しなくてよい）。

- **結合ルール**: `type` が証拠 かつ `evidence_number` が等しい FileEntry を、1つの号証PDFに結合する。
  グループが1ファイルだけなら結合せずそのまま（押印のみ）。
- **並び順**: 枝番の昇順（各 FileEntry の `stamps[].branch` の最小値）。枝番が無い／同値のときは
  `files[]` の出現順。**AI は同一号証のファイルを枝番順に並べて出力すること**。
- **ページ番号**: 各 FileEntry の `stamps[].page` は**そのファイル内の1始まり**。結合時にアプリが
  ページオフセットを付与する（AIはファイルごとのローカルページで指定すればよい）。
- **出力ファイル名**: アプリが `evidence_number` から決定的に生成する（結合時の名前ブレ防止のため、
  各ファイルの `suggested_base_name` には依存しない）。

### 整合性の安全策（重要）
`evidence_number` が唯一の結合キーなので、AI出力の不整合は誤結合に直結する。

- AI は**同一号証の全パートで `evidence_number` を完全一致**させること（表記ゆれ・桁ゆれ厳禁）。
- グループ内で**枝番の重複・欠落・順序不明**があれば、当該ファイルの `needs_user_confirmation` を true にする。
- アプリは結合グループを検出したら、**プレビューで結合後の全ページと押印位置を人に見せ、承認後に書き出す**
  （自動結合でも人の最終確認は必須。意図しない結合はプレビューで分離できる）。

## 座標系の定義（最重要・厳守）

スタンプ位置の解釈で食い違うと事故になるため、以下を唯一の基準とする。

1. **基準面**: `rotate_degrees` を適用して**正立表示した後の紙面**。
   （＝人が読める向きに直した状態。回転前の生データ座標ではない）
2. **原点と向き**: 紙面の**左上が (0,0)**、x は右方向、y は**下方向**。
3. **正規化**: x,y は紙面の幅・高さに対する 0〜1 の比率（用紙サイズ非依存）。
4. **`anchor`**: (x,y) に合わせる**ラベル外接枠の基準点**。
   `top-right`（既定）なら「ラベルの右上角を (x,y) に置く＝そこから左下へ字が伸びる」。
   取りうる値: `top-left | top-right | bottom-left | bottom-right | center`。

> 例: 右上に置きたい → `{ "x": 0.93, "y": 0.05, "anchor": "top-right" }`

## AIへの指示ルール（プロンプトに反映する指針）

- **番号**: `evidence_number` は記号＋ゼロ埋め3桁（甲001）。`branch_range` はファイル全体の枝番範囲。
  スタンプ文字列は出力しない（アプリが生成）。
- **ページごとの押印**: `stamps[]` に**1ページ1要素**で入れ、各要素に `branch`（このページの枝番。なければ null）を付ける。
  枝番が複数ページにまたがるときは原則先頭ページにだけ要素を作る（続きページは入れない）。
- **回転**: 紙面が読める向きになる補正角を各要素の `rotate_degrees` に入れる。既に正立なら 0。
- **位置**: 既定は右上（`anchor: top-right`, x≈0.93, y≈0.05）。
- **干渉回避**: 本文の文字・押印・**mintsのタイムスタンプ帯**と重なる場合は、
  正規化座標を動かして空きスペースへずらす。
- **余白確保**: 印刷切れ防止のため極端な端は避ける（目安 x ≤ 0.95 / y ≥ 0.03、四辺3%以上の余白）。
- **手書き済み**: その要素の `draw_label: false`（番号は押さず回転補正のみ）。
- **迷ったら確認**: 押す位置・ページ・枝番に少しでも確証がなければ `needs_user_confirmation: true`。

## 既定値（AIが省略した場合のアプリ側補完）
※ `stamps[]` の各要素に適用。
| 項目 | 既定 |
|---|---|
| `schema_version` | `"1.0"` 相当 |
| `stamps[].branch` | null（枝番なし） |
| `stamps[].draw_label` | true |
| `stamps[].rotate_degrees` | 0 |
| `stamps[].position.anchor` | `top-right` |
| `stamps[].position` 全体省略 | 右上（x=0.93, y=0.05, top-right） |
| `stamps[].font_size_pt` | 18 |
| `stamps[].color` | `#C80000` |

## アプリ側の検証責任（受け取り時にチェックすること）
- `evidence_number`＋`branch` から生成したスタンプ文字列の**未収録文字をフォントで確認**し、あれば警告
  （フォント文字セットは [`../assets/fonts/README.md`](../assets/fonts/README.md) 参照）。
- 各 `stamps[].rotate_degrees` は 0/90/180/270 に丸める。
- 各 `stamps[].position.x`,`y` は 0〜1 にクランプ。
- 各 `stamps[].page` は範囲内か確認（範囲外はエラー表示し当該ファイルをスキップ）。
- `needs_user_confirmation: true` の項目は、承認まで書き出さない。
- **同一 `evidence_number` のグループを検出**して結合候補にする。枝番の重複・欠落・順序不明は警告し確認に回す。
- **必ずプレビュー → 人が承認 → 書き出し**。自動結合・自動確定はしない（結合結果も承認対象）。
